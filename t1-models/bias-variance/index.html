    Bias, Variance and Tuning¶

    70 min Classic models Reference, no tasks

    Every page in this group has had a knob that trades fit against stability: alpha, C, gamma, max_depth, ccp_alpha, learning rate. They are all the same knob. This page explains what it is turning and how to decide where to set it.

    Why this matters¶

    Two words have been used repeatedly without being defined. The Tree-Based page said bagging reduces variance and boosting reduces bias. That sentence is exactly right and means nothing until you have this page.

    More practically, this is where you learn to answer three questions that come up in every project:

    • Is my model too simple or too complex?
    • Would collecting more data help, or am I wasting the budget?
    • How do I choose the settings without fooling myself?

    Bias and variance¶

    Imagine training your model many times on different samples from the same population. Each time you get a slightly different model, and each makes predictions.

    Bias is how far the average prediction lands from the truth. A high bias model is consistently wrong in the same direction, because it is too simple to represent the pattern. Underfitting.

    Variance is how much the predictions move when the training data changes. A high variance model gives you a different answer every time, because it is fitting the particular rows it saw rather than the pattern behind them. Overfitting.

    Noise is the part nobody can remove. Two identical customers do different things.

    \[ \text{total error} = \text{bias}^2 + \text{variance} + \text{noise} \]

    You can trade the first two against each other. You cannot touch the third.

    The trade¶

    Making a model more flexible lowers bias and raises variance. Constraining it does the reverse. There is a point in between where the sum is smallest, and finding it is what tuning means.

    Model Bias Variance Why
    Linear regression High Low It can only draw a straight line, but it draws the same one every time
    Deep decision tree Low High It can represent anything, including the noise
    Random forest Low Lower Many high variance trees, averaged
    Boosted trees Lower Higher Each round attacks the remaining bias
    K-nearest neighbours, k=1 Very low Very high The boundary follows individual points
    K-nearest neighbours, k=50 Higher Lower Each answer is an average of fifty

    This table is the sentence from the Tree-Based page, unpacked. Bagging attacks variance by averaging independent mistakes. Boosting attacks bias by repeatedly going after what is still wrong, which is why it can overfit and a forest rarely does.

    The one-line version

    Bias is being wrong in a way more data will not fix. Variance is being wrong in a way more data will fix.

    The floor¶

    Some error is irreducible. Two customers with identical features churn differently, because the feature set does not contain whatever made the difference.

    That matters for a practical reason: it tells you when to stop. If the best achievable accuracy on your problem is around 85 percent and you are at 83, the remaining work is in getting better features or better data, not in tuning. A model that reaches 99 percent on a genuinely noisy problem has not beaten the floor, it has found a leak.

    Diagnosing which problem you have¶

    Start with the two scores.

    Training Validation Diagnosis Do this
    Low Low High bias More flexible model, better features
    High Much lower High variance Regularise, simplify, more data
    High High You are done Stop
    Low Higher Something is broken Check your split

    That last row is worth knowing. Validation scoring above training usually means a leak, a badly shuffled split, or a validation set that happens to be easier. It is a bug, not a success.

    Learning curves¶

    The two-score table tells you which problem you have. A learning curve tells you whether more data would fix it, which is often a budget question rather than a technical one.

    from sklearn.model_selection import learning_curve
import numpy as np

sizes, train_scores, val_scores = learning_curve(
    model, X_train, y_train, cv=5,
    train_sizes=np.linspace(0.1, 1.0, 10), scoring="roc_auc",
)
train_mean = train_scores.mean(axis=1)
val_mean = val_scores.mean(axis=1)

    Read the right-hand end of the plot.

    Both curves have met, at a low score. High bias. The model is as good as it can be and it is not good. More data changes nothing. Change the model or the features.

    A wide gap remains and the validation curve is still climbing. High variance. More data would help, and so would regularisation in the meantime.

    Both curves have met, at a high score. You are finished. Spend your time elsewhere.

    ML connection

    The Plotting page listed the learning curve as one of the five charts you would make in every project and promised it for trimester two. Here it is early, because it answers a question people ask in week one: should we collect more data?

    Draw this before anybody spends money on collection. It is a fifteen line answer to a expensive question.

    Validation curves¶

    A learning curve varies the amount of data. A validation curve varies one hyperparameter and holds everything else fixed.

    from sklearn.model_selection import validation_curve

alphas = np.logspace(-3, 3, 13)
train_scores, val_scores = validation_curve(
    Ridge(), X_train, y_train, param_name="alpha",
    param_range=alphas, cv=5, scoring="r2",
)

    Every knob in this group produces a curve of this shape. Only the axis label changes. Left side is too constrained, right side is too flexible, and the minimum of the validation curve is where you set it.

    Two things to read off the picture. The gap between the lines is your variance. The height of the lower line is your bias plus the noise floor.

    Every knob, on one page¶

    This is the reference. Different libraries, different names, one idea: each of these trades accuracy on the training data for stability on new data.

    Three more that are not parameters at all:

    More training data reduces variance and leaves bias untouched.

    Fewer features reduces variance. This is what Lasso did for you automatically.

    Ensembling reduces variance for free, which is why a random forest with default settings is such a reliable first model.

    Families of technique¶

    When you meet a regularisation method that is not on this list, it will be one of these six.

    Constrain the capacity. Limit what the model is able to represent. max_depth, the degree of a polynomial, the number of neighbours.

    Penalise size. Add a cost for large parameters. Ridge, Lasso, ccp_alpha.

    Add randomness. Force the model not to rely on any one thing. Bootstrap samples, random feature subsets, and dropout when you meet neural networks in trimester two.

    Stop early. Halt training at the point where validation error turns upward. Boosting rounds now, training epochs later.

    Get more data. Including making more from what you have, which is data augmentation in trimester two.

    Ensemble. Average several models so their independent errors cancel.

    Searching for the settings¶

    You have been changing one parameter at a time by hand. That works for one knob and falls apart at two, because parameters interact. C and gamma in an SVM are the standard example: the best gamma depends on the C you chose.

    from sklearn.model_selection import GridSearchCV

grid = {
    "clf__n_estimators": [200, 400],
    "clf__max_depth": [3, 5, 8],
    "clf__min_samples_leaf": [1, 5, 20],
}
search = GridSearchCV(pipeline, grid, cv=5, scoring="roc_auc", n_jobs=-1)
search.fit(X_train, y_train)
print(search.best_params_, search.best_score_)

    Grid search tries every combination. Eighteen here, each trained five times, so ninety fits. The cost multiplies with every parameter you add.

    Random search samples combinations instead, and with more than two or three parameters it usually wins for the same budget. The reason is in the diagram: in most problems one parameter dominates and the others barely matter. A grid spends its budget on a handful of values of the important one. A random search tries a different value of it every single time.

    from sklearn.model_selection import RandomizedSearchCV
from scipy.stats import randint, loguniform

distributions = {
    "clf__n_estimators": randint(100, 800),
    "clf__max_depth": randint(2, 12),
    "clf__learning_rate": loguniform(0.01, 0.3),
}
search = RandomizedSearchCV(pipeline, distributions, n_iter=40, cv=5, n_jobs=-1)

    Sample learning rates and alphas on a log scale. The difference between 0.01 and 0.1 matters enormously and the difference between 0.21 and 0.22 does not.

    Search inside the pipeline, never outside it

    Note clf__n_estimators with a double underscore. That is how you reach a step inside a pipeline.

    Putting the whole pipeline into the search means the scaler and the encoder are refitted on the training fold of every split. Search the model alone, after transforming the data once, and every fold has seen the statistics of every other fold. That is the leakage from the Data Preprocessing page, arriving through the back door.

    Tuning without cheating¶

    Here is the subtle failure, and it catches people who have done everything else right.

    You try a hundred configurations and keep the one with the best validation score. That score is now optimistic, because you selected it for being high. Some of its advantage is real and some is luck, and you have no way to tell which.

    The fix is that the test set is touched once, at the very end, after all decisions are made.

    search.fit(X_train, y_train)
print("validation:", search.best_score_)
print("test:", search.score(X_test, y_test))

    Expect the test score to be a little lower. That gap is the price of having searched, and reporting the validation score as your result is how people end up promising something they cannot deliver.

    When the decisions themselves need an honest estimate, nested cross-validation puts a search inside every outer fold. It is expensive and worth knowing the name of, and for the projects in this group a single held back test set is enough.

    Keeping what you built¶

    A tuned model that only exists in a notebook kernel is not a result.

    import joblib

joblib.dump(search.best_estimator_, "models/churn_pipeline.joblib")
model = joblib.load("models/churn_pipeline.joblib")
print(model.predict(X_test[:5]))

    Save best_estimator_, not the search object, and note that it is the whole pipeline: scaler, encoder and model together. Load it somewhere else and it transforms raw columns exactly the way it did during training, which is the point of having built it as one object.

    A saved model is a snapshot of three things

    The code, the data it was trained on, and the library versions. Load a pipeline saved by a different scikit-learn version and it may warn, misbehave or refuse.

    Save the version alongside it, in a filename or a small text file. This is the same reproducibility problem from the Data Preprocessing page, now applied to the model rather than the data.

    When it goes wrong¶

    My validation score is higher than my training score

    A leak, an unshuffled split, or a validation set that happens to be easier. Investigate rather than celebrate.

    The grid search takes hours

    Too many combinations. Switch to RandomizedSearchCV, reduce the folds while exploring, set n_jobs=-1, and search on a subsample first to find the promising region.

    The best parameter is at the edge of my range

    Your range was too narrow. Extend it in that direction and search again.

    The learning curve is still rising at the right edge

    More data would help. That is a finding worth reporting, and it may be more valuable than any tuning you could do.

    Tuning barely changed my score

    Common and not a failure. The gains in machine learning come mostly from features and data. If tuning moves you half a point, that is normal, and it is a signal to go back to the long loop from the Classification page.

    best_score_ and the test score disagree a lot

    You searched too hard on too little data. Reduce the number of configurations, or accept that your test set is small and report the uncertainty alongside the number.

    Check yourself¶

    1. Train a very deep tree and a depth-two tree on the same data. Report both scores for each and label which suffers from bias and which from variance.
    2. Draw a learning curve for one model. Say whether more data would help and how you know.
    3. Draw a validation curve for max_depth. Mark the minimum and explain what is happening on each side of it.
    4. Run a grid search over three parameters, then a random search with the same number of fits. Compare the best scores.
    5. Report your best validation score and your test score for the same model. Explain the gap in one sentence.
    6. Take one model and reduce its variance three different ways. Record what each did to both scores.

    Questions to sit with¶

    1. Bias is being wrong in a way more data will not fix. Name a problem where you suspect the bias comes from the features available rather than the model.
    2. Some error is irreducible. How would you estimate that floor for a real problem, and what would you do with the number?
    3. You tried a hundred configurations and kept the best. In what sense is that score dishonest, and how much does it matter?
    4. Random search beats grid search because one parameter usually dominates. What does that say about the effort people spend tuning the others?
    5. Tuning typically moves a score by less than a point, while better features can move it by ten. Why do you think tuning gets so much more attention?
