    Tree-Based Models¶

    85 min Classic models Needs: Classification, Linear Models

    A linear model adds everything up. A tree asks a series of yes or no questions. That difference makes trees the easiest models to read and, once you combine enough of them, the strongest thing you will run on a table all year.

    Why this matters¶

    On tabular data like the churn file, a gradient boosted ensemble is very often the best model available. Not a neural network, which comes into its own on images, audio and text in trimester two. If somebody hands you a spreadsheet and asks for the best possible prediction, this page is the answer.

    Trees are also where you meet ensembles: the idea that many mediocre models combined can beat one carefully built model. That idea turns up everywhere afterwards.

    How a tree decides¶

    A tree has one move, repeated. Pick a feature, pick a threshold, split the data in two, and do it again on each side.

    The only question is which split to make.

    The tree scores every possible split by how pure the resulting groups are. A group that is all churners or all stayers is pure. A fifty-fifty group is as impure as it gets.

    Two ways to measure it, and they rarely disagree:

    Gini impurity is the chance that two items drawn at random from the group have different labels. Zero when the group is pure, 0.5 at its worst for two classes.

    Entropy is the same idea from information theory, and you have met it. It is the average surprise of a label drawn from the group, measured with the same logarithm that produced cross-entropy on the Probability page.

    Gini is slightly faster, entropy is slightly more sensitive to rare classes, and the trees they produce are usually near identical. Do not spend time on the choice.

    Reading this picture both ways is the thing to take from it. Each question is a straight cut parallel to an axis, so the leaves are rectangles. That is the axis-aligned boundary from the Classification page, now explained.

    It is also why trees need no scaling. A split asks whether a value is above a threshold, and that answer does not change if you multiply the column by a thousand.

    from sklearn.tree import DecisionTreeClassifier

tree = DecisionTreeClassifier(random_state=42)
tree.fit(X_train, y_train)
print(tree.score(X_train, y_train), tree.score(X_test, y_test))

    1.0  0.727

    Perfect on training data and worse than the baseline on test data. A tree left unconstrained will keep splitting until every leaf is pure, which means it has memorised the training set. This is overfitting in its purest form, and fixing it is the next two sections.

    Reading the rules¶

    The reason to care about a single tree is that you can read it.

    from sklearn.tree import export_text, plot_tree
import matplotlib.pyplot as plt

print(export_text(tree, feature_names=list(X_train.columns), max_depth=3))
fig, ax = plt.subplots(figsize=(16, 8))
plot_tree(tree, feature_names=X_train.columns, class_names=["stay", "churn"],
          max_depth=3, filled=True, ax=ax)

    Set max_depth on the display, not just on the model. A full tree on this dataset has thousands of nodes and the picture is unreadable.

    Each node tells you the question, how many samples reached it, how they were distributed, and the impurity. Following one path from root to leaf gives you a rule in plain language: short tenure, month to month contract, fiber internet, predict churn.

    ML connection

    This is the most explainable model in the whole programme. A doctor or a loan officer can read a path and agree or disagree with it.

    Keep that in mind when you reach the ensembles later on this page. Five hundred trees voting are far more accurate and cannot be read at all, and that trade is a real decision rather than an obvious one.

    Pre-pruning¶

    The first fix is to stop the tree before it goes too far.

    tree = DecisionTreeClassifier(
    max_depth=5,
    min_samples_leaf=50,
    min_samples_split=20,
    random_state=42,
)
    Parameter What it does
    max_depth How many questions deep the tree may go
    min_samples_leaf A leaf must contain at least this many samples
    min_samples_split A node needs at least this many before it may split
    max_leaf_nodes A hard cap on the number of leaves
    min_impurity_decrease A split must improve purity by at least this much

    min_samples_leaf is the one to reach for first. A leaf built from three customers is noise dressed as a rule, and setting a floor removes a whole class of nonsense.

    These are guesses, though. You are deciding in advance how complex the answer should be, without knowing.

    Post-pruning¶

    The second fix grows the tree fully and then cuts branches back, keeping only those that earn their place.

    Cost complexity pruning scores the whole tree as its error plus a penalty per leaf. The size of that penalty is ccp_alpha.

    \[ \text{cost} = \text{error} + \alpha \times (\text{number of leaves}) \]

    This is the same trade you met with Ridge and Lasso: fit against complexity, with one knob controlling the exchange rate. There, the penalty was on the size of the coefficients. Here it is on the number of leaves.

    scikit-learn will give you every alpha at which the tree changes shape.

    path = tree.cost_complexity_pruning_path(X_train, y_train)
alphas = path.ccp_alphas[:-1]
print(len(alphas), alphas.min(), alphas.max())

    The last value is dropped because it prunes the tree down to a single leaf.

    Then train one tree per alpha and see which does best on held back data.

    from sklearn.model_selection import cross_val_score
import numpy as np

scores = []
for alpha in alphas:
    clf = DecisionTreeClassifier(random_state=42, ccp_alpha=alpha)
    scores.append(cross_val_score(clf, X_train, y_train, cv=5).mean())
best_alpha = alphas[int(np.argmax(scores))]
print(best_alpha, max(scores))

    Use cross-validation rather than a single split for this, and never the test set. Choosing alpha by looking at test scores means the test set has helped build the model, which is the leakage you read about two pages ago.

    In practice people use both kinds of pruning: a sensible max_depth to keep training fast, then ccp_alpha chosen by cross-validation to do the fine work.

    Many trees are better than one¶

    A single tree has a real weakness beyond overfitting: it is unstable. Change a handful of rows and the top split can change, and every branch below it moves.

    That instability turns out to be useful. Build many trees that are each unstable in a different direction, and the errors cancel out.

    Bagging trains many trees at the same time on different random samples of the data, then averages their votes. Because the trees are independent, their mistakes are independent, and averaging cancels them. Bagging reduces variance and is very hard to overfit.

    Boosting trains trees one after another, each one focused on what the previous ones got wrong. It reduces bias, is usually more accurate, and will overfit if you let it run too long.

    Bagging Boosting
    Trees are built In parallel, independently In sequence, each depending on the last
    Each tree is Deep and overfitted Shallow and weak
    It reduces Variance Bias
    Overfits Rarely Yes, if unchecked
    Tuning Forgiving Fiddly, and worth it

    Random forests¶

    A random forest is bagging with one extra idea.

    from sklearn.ensemble import RandomForestClassifier

forest = RandomForestClassifier(
    n_estimators=300,
    max_features="sqrt",
    min_samples_leaf=5,
    random_state=42,
    n_jobs=-1,
)
forest.fit(X_train, y_train)
print(forest.score(X_test, y_test))

    Two sources of randomness, and the second is what makes it a forest rather than just bagged trees.

    Bootstrap sampling. Each tree sees a random sample of the rows, drawn with replacement, so each one sees a slightly different dataset.

    Random feature subsets. At every split, each tree may only consider a random subset of the features, sqrt of them by default for classification.

    The second one matters more than it looks. Without it, if one feature is strongly predictive, every tree puts it at the root and all the trees end up nearly identical. Forcing them to ignore it sometimes produces genuinely different trees, and different trees are the entire point.

    n_estimators is the one parameter you do not need to tune carefully. More trees never hurt accuracy, they only cost time. Three hundred is plenty, and the curve is flat long before that.

    n_jobs=-1 uses every core on your machine. The trees are independent, so this is free speed.

    Feature importance, and its traps¶

    A forest can tell you which features it relied on.

    import pandas as pd

importances = pd.Series(forest.feature_importances_, index=X_train.columns)
print(importances.sort_values(ascending=False).head(10))

    This is impurity-based importance: how much each feature reduced impurity, totalled across every split in every tree. It is free, because it was computed during training, and it has two serious biases.

    Impurity importance inflates some features and splits others

    It favours features with many distinct values. A continuous column offers hundreds of possible thresholds, so it gets more chances to look useful than a yes or no column. An ID column, if you forgot to drop it, will top the chart.

    It splits credit between correlated features. If tenure and TotalCharges carry the same information, the forest uses each about half the time and both appear half as important as either one really is. You saw that correlation on the heatmap during preparation, which is why you drew it.

    Permutation importance avoids both problems. Shuffle one column, see how much the score drops, put it back, repeat.

    from sklearn.inspection import permutation_importance

result = permutation_importance(forest, X_test, y_test, n_repeats=10, random_state=42)
perm = pd.Series(result.importances_mean, index=X_test.columns)
print(perm.sort_values(ascending=False).head(10))

    It is slower, it measures importance on held back data rather than training data, and it answers a more honest question: how much does the model's performance actually depend on this column?

    The correlated-features problem remains, in a different form. Shuffle one of two correlated columns and the model leans on the other, so both look unimportant. There is no way around this except knowing your data.

    For explaining individual predictions rather than the model as a whole, SHAP from the Linear Models page works on trees too, and has a fast implementation designed for them.

    Boosting¶

    Each tree in a boosted ensemble is deliberately weak, often only two or three levels deep. Alone it is barely better than guessing. In sequence, each one attacking what is left over, they become the strongest tabular models available.

    AdaBoost was the original. After each round it increases the weight of the examples that were misclassified, so the next tree pays more attention to them. Simple, and sensitive to noisy labels, because a mislabelled row gets weighted up round after round.

    Gradient boosting is the modern approach and the one to understand. Instead of reweighting rows, each new tree is trained to predict the residual, which is what the ensemble so far got wrong. Add its prediction to the running total and the error shrinks. It is gradient descent, with a tree as the step.

    from sklearn.ensemble import AdaBoostClassifier, GradientBoostingClassifier

ada = AdaBoostClassifier(n_estimators=200, random_state=42)
gb = GradientBoostingClassifier(
    n_estimators=300,
    learning_rate=0.05,
    max_depth=3,
    random_state=42,
)

    Three parameters matter and they interact:

    learning_rate shrinks each tree's contribution. Smaller means slower and usually better, because no single tree can dominate.

    n_estimators is how many rounds. Unlike a forest, more is not always better: past a point the ensemble starts fitting noise.

    max_depth controls how complex each weak learner is. Two to four is normal. Deep trees in a boosted ensemble overfit quickly.

    Low learning rate with many estimators is the reliable combination. Start at 0.05 and 300.

    XGBoost and LightGBM¶

    Both are gradient boosting, engineered hard.

    XGBoost added regularisation to the tree-building objective, handles missing values natively, and was fast enough to win most tabular competitions for years.

    LightGBM grows trees leaf by leaf instead of level by level and bins continuous features before training. Much faster on large data, and slightly more prone to overfitting small datasets.

    Both live outside scikit-learn and follow the same interface, so swapping them in is one line.

    from lightgbm import LGBMClassifier

model = LGBMClassifier(n_estimators=400, learning_rate=0.05, random_state=42)

    scikit-learn's own HistGradientBoostingClassifier uses the same binning idea, is fast, needs no extra install, and is a perfectly good default.

    The order worth trying on a new table

    A dummy baseline. Then logistic regression, for the explanation. Then a random forest, which usually works with no tuning at all. Then gradient boosting, which usually wins and needs some care.

    Stop at the first one that is good enough for what you need. Every step beyond costs you interpretability and time.

    Evaluating them¶

    Everything from the Classification page applies without change: confusion matrix, precision, recall, F1, ROC AUC, the metric chosen before you see the scores, and always against the dummy baseline.

    from sklearn.metrics import classification_report, roc_auc_score

pred = forest.predict(X_test)
proba = forest.predict_proba(X_test)[:, 1]
print(classification_report(y_test, pred))
print(roc_auc_score(y_test, proba))

    Two things specific to trees.

    Class weights. Tree models accept class_weight="balanced", which makes the minority class count for more during training. On imbalanced data like churn it is often a bigger improvement than any amount of tuning.

    Probabilities from a forest are the proportion of trees that voted for the class. They are reasonable but not well calibrated, so if you need the number itself to mean something rather than just to rank, look at CalibratedClassifierCV.

    When it goes wrong¶

    Training accuracy is 1.0 and test accuracy is poor

    An unpruned tree. Set max_depth and min_samples_leaf, then tune ccp_alpha with cross-validation.

    plot_tree produces an unreadable mess

    Pass max_depth=3 to the plotting call and make the figure larger. For a full description use export_text instead.

    The most important feature is an ID or a date

    You forgot to drop an identifier, or you have a leaking feature. Both were covered on the Data Preprocessing page and both show up first in an importance chart.

    Two features I know matter both look unimportant

    They are correlated, so the forest and the permutation test both split the credit between them. Check the correlation heatmap, and consider dropping one.

    My boosted model is worse than the forest

    Usually the learning rate is too high, the trees are too deep, or you ran too many rounds. Try learning_rate=0.05, max_depth=3, and watch the validation score as rounds increase.

    The forest takes forever

    Set n_jobs=-1, lower n_estimators while experimenting, and raise min_samples_leaf. Accuracy barely changes and training time falls sharply.

    2. Print the first three levels of the rules and translate one root-to-leaf path into plain language.
    3. Pre-prune with three different max_depth values and record what happens to both scores.
    4. Get the pruning path, train a tree for each alpha, and plot accuracy against alpha. Mark the best one and say how you chose it.
    5. Train a random forest and compare it with your best single tree. Report the improvement and the cost.
    6. Compare impurity importance with permutation importance on the same forest. Name a feature that moves, and explain why.
    7. Train AdaBoost and gradient boosting. Then halve the learning rate and double the estimators, and describe what changed.

    Questions to sit with¶

    1. A single tree can be read by the person it affects. Five hundred trees cannot, and score several points higher. Who should decide which to deploy, and what would you need to tell them?
    2. Pre-pruning fixes the complexity in advance and post-pruning lets the data choose. Where else have you seen that distinction, and which do you instinctively prefer?
    3. Impurity importance favours features with many distinct values. How many published "most important factor" claims do you think survive that fact?
    4. Bagging works because the trees make independent mistakes. What would make them stop being independent, and what would that do to the forest?
    5. Boosting keeps attacking the errors that remain. On a dataset with some mislabelled rows, what is it eventually attacking?
